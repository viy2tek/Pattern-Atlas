# Agent instructions

## Release and versioning policy

Release Please and the GitHub Actions release workflow are the sole authority for versions, changelog entries, tags, release assets, and GitHub Releases.

Do not manually change version fields in `pyproject.toml`, Python modules, manifests, documentation, or other project files.

Do not create or move Git tags. Do not create or publish GitHub Releases. Do not edit `CHANGELOG.md` for a release, and do not run `gh release create`.

Use Conventional Commit messages and Conventional Commit pull request titles. Allowed types are `feat`, `fix`, `perf`, `refactor`, `docs`, `build`, `ci`, `chore`, `test`, `style`, and `revert`. Add a useful scope when one is clear, such as `fix(ui):` or `feat(export):`.

For versions below `1.0.0`, ordinary features and fixes produce patch releases. Mark a change as breaking with `!` or a `BREAKING CHANGE:` footer only when the user explicitly requests a compatibility-breaking release. Do not decide to advance a minor or major version manually.

Describe every user-visible change accurately in the pull request title and body so Release Please can generate a complete changelog. The Release PR generated by Release Please is the only normal place where version fields and `CHANGELOG.md` change.
